3. V0 Assumptions and Boundaries
3.1 In scope
• One active search per renter
• Hyderabad inventory
• Listing types:

• Multiple active searches per renter

7. Initial Inventory Selection
The worker does not load every database row blindly. V0 should apply inexpensive deterministic prefilters before full evaluation.
7.1 Eligible listing conditions
A listing can enter matching when:
• Admin approved it.
• content_type = PROPERTY_LISTING.
• It belongs to Hyderabad in V0.
• It has a supported listing type.
• It is not explicitly UNAVAILABLE.
UNKNOWN, AVAILABLE, and STALE listings may enter matching.
7.2 Useful database prefilters
Safe prefilters include:
• approved = true
• city = 'Hyderabad'
• availability_status != 'UNAVAILABLE'
• listing type in supported types
Potentially apply explicit cheap constraints such as incompatible listing type before loading a large record, but the application-level evaluator remains the source of truth.

13.1 Why normalization over known facts matters
If parking is unknown, it should not silently count as failed parking. Removing that factor from the denominator preserves the listing's estimated fit while completeness communicates uncertainty.
13.2 Minimum score evidence
To avoid absurdly high fit based on only one known field, V0 should require a minimum core evidence set before treating the score as actionable.
Recommended core evidence for actionable ranking:
• listing type known
• locality known
• rent known
If fewer than these three are known, store the evaluation but classify it as NEEDS_QUALIFICATION or data-quality review regardless of numerical fit.

17.4 POSSIBLE_MATCH

24. Pausing and Closing Search
24.1 Pause
When search becomes PAUSED:
• Do not evaluate newly approved inventory for that search.
• Preserve all historical matches.
• Do not initiate new outreach.
• Existing confirmed visits remain intact.
24.2 Resume
When resumed:
• Set status back to ACTIVE.
• Queue a catch-up matching job so listings added during the pause can be evaluated.
24.3 Close
When CLOSED:
• Stop new matching.
• Stop new outreach.
• Preserve historical data.
• Existing visit cancellation/resolution may still be supported as a separate workflow.
25. Handoff to Qualification
Matching does not itself contact the owner/broker/current tenant.
When the renter clicks Contact Them:

The qualification workflow consumes match.gaps in priority order.
After every inbound reply:
1. LLM extracts explicit facts.
2. Backend updates canonical listing facts.
3. Matching engine re-evaluates the listing for that renter.
4. Explicit new hard contradiction -> REJECTED and conversation closes politely.
5. Remaining important gaps -> ask next relevant question.
6. All necessary facts resolved -> QUALIFIED -> scheduling workflow.
This reuse of the same matching engine is important. Qualification should not contain a second, inconsistent definition of what a good match means.

27. Contradictory Listing Data
Important contradictions should normally have been resolved during admin ingestion.
If unresolved canonical contradiction somehow reaches matching:
• Do not let the matcher guess.
• Mark affected canonical field as unknown/untrusted.
• Add a data-quality or qualification gap.
• Prevent STRONG_MATCH classification when the contradiction touches a core/hard-boundary fact.
Examples:
• Rent is both 22k and 24k
• Two incompatible localities
• Conflicting availability dates
Admin correction has higher authority than original source text for canonical V0 storage.

36. Concurrency and Idempotency
The system must remain correct when:
• renter taps Start Search twice
• same Telegram update is delivered twice
• worker retries a job after restart
• same listing is approved twice by a duplicate callback
• a listing changes while the search worker is running
V0 safeguards:
1. Search and listing carry versions.
2. Match upsert stores versions used for evaluation.
3. Unique job keys prevent duplicate initial jobs.
4. Unique notification keys prevent duplicate renter messages.
5. State transitions verify current state before writing.
6. Re-evaluate if listing/search version changed materially during a long job.
A stale evaluation is preferable to a duplicate irreversible action, but current version checks should minimize both.

39. Minimum Test Matrix
39.1 Hard constraints
• wrong listing type -> reject
• excluded locality -> reject
• rent above hard max -> reject
• required amenity false -> reject
• required amenity unknown -> not reject
• move-in date too late -> reject
• move-in unknown -> gap
• unavailable listing -> reject
• stale listing -> not reject
39.2 Scoring
• preferred locality scores above acceptable locality
• target-budget listing scores above near-max listing
• unknown preferred amenity does not count as false
• known preferred mismatch lowers fit
• all known positive preferences produce high fit
• personalized location-heavy weights change ranking predictably
39.3 Completeness
• unknown availability lowers completeness
• unknown required fact lowers completeness more than optional preference
• unrelated fields do not affect completeness
• STALE availability does not count as fresh availability knowledge
39.4 Classification
• high fit + high completeness + available -> strong
• high fit + required unknown -> needs qualification
• high fit + stale availability -> needs qualification
• medium fit -> possible
• hard violation -> rejected regardless of otherwise high score
39.5 Start Search workflow
• missing core requirements -> no activation
• first click -> active + one job
• duplicate click -> no duplicate job
• worker restart -> safe retry
• results notification sent once
• search remains active after initial run
39.6 Event-driven re-evaluation
• new listing evaluated against active search
• new listing ignored for paused search
• resume performs catch-up
• requirement update increments version and reruns inventory
• listing update changes existing match
• unavailable update converts affected match to rejected
40. Acceptance Criteria
The Start Search and matching feature is complete for V0 when all of the following are true:
1. A renter with complete core requirements can click Start Search in Telegram.
2. Search state becomes ACTIVE exactly once.
3. Initial inventory matching runs asynchronously and idempotently.
4. Explicit hard contradictions reject listings.
5. Unknown fields never behave as false by default.
6. Deterministic fit score is produced from known applicable facts.
7. Information completeness is calculated separately.
8. Important unknowns become structured qualification gaps.
9. Strong, qualification-needed, possible, and rejected outcomes behave consistently.
10. Renter receives a concise initial result summary and useful top candidates.
11. No outbound contact happens without renter approval.
12. Newly approved listings are automatically evaluated against active searches.
13. Requirement and listing updates trigger deterministic re-evaluation.
14. Matching decisions are explainable from persisted score breakdown/reasons.
15. Automated tests cover core hard-constraint, scoring, completeness, classification, and idempotency behavior.
41. Implementation Order
Recommended engineering sequence:

The optional LLM soft-context step should be implemented only after the deterministic core is tested with real Hyderabad examples.
42. Design Decisions to Preserve
A coding agent implementing this feature should preserve these decisions unless the product specification is explicitly changed:
• Start Search means activate a persistent search, not run a one-time query.
• No scraping occurs as part of Start Search in V0.
• Unknown is not false.
• Only explicit hard contradiction rejects.
• Fit and completeness are separate.
• Core matching is deterministic.
• LLM reasoning is bounded to unstructured soft context and language understanding.
• The same evaluator is reused after new facts arrive during qualification.
• First outreach requires renter approval.
• New approved inventory automatically flows into active searches.
• Persist reasons and gaps so decisions are explainable and recoverable.
