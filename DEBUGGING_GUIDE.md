# FlatHunter Debugging & Inspection Guide

This guide explains how to debug incoming/outgoing Telegram messages, LLM prompt-response pairs, latency, and errors using the built-in local tracing tools.

---

## 1. Quick CLI Inspection Commands

All logs and traces are written in real-time to the `logs/` directory. You can query and tail them using the built-in CLI tool:

### 🔍 Search all events for a specific user
Shows every Telegram message sent by the user, the bot's replies, and all triggered LLM calls:
```powershell
python -m app.tools.inspect_logs --user 1020615388
```

### ⚡ View only LLM calls, prompts, and structured JSON responses
Filters out normal message chatter and displays only the exact prompt strings sent to the model, schema definitions, parsed outputs, and latency:
```powershell
python -m app.tools.inspect_logs --user 1020615388 --type LLM_CALL
```

### ⚠️ View only errors across the whole application
Filters for rate limits (429), not found (404), schema validation errors, or unhandled exceptions:
```powershell
python -m app.tools.inspect_logs --errors
```

### 👀 Live tail events in real-time
Watch incoming updates and LLM calls live in your terminal as you interact with the bot in Telegram:
```powershell
python -m app.tools.inspect_logs --tail
```

### 🔢 Limit the number of records displayed
By default, the tool shows the last 20 events. You can change this using `--limit`:
```powershell
python -m app.tools.inspect_logs --user 1020615388 --limit 50
```

## 2. Direct File Inspection (Inside VS Code / Cursor)

If you prefer viewing the raw JSON data directly in your editor:

| File Path | Description |
| :--- | :--- |
| `logs/traces.jsonl` | Master event log containing all inbound/outbound Telegram messages, LLM requests/responses, and errors across all users. |
| `logs/users/<telegram_user_id>.jsonl` | **Per-user log file.** Opening `logs/users/1020615388.jsonl` gives you a 1-click view of that user's entire conversation history and AI extractions. |
| `logs/app.log` | Standard console output log. |

## 3. Log Event Structure

Every line in `traces.jsonl` and `logs/users/<id>.jsonl` is a self-contained JSON object:

```json
{
  "timestamp": "2026-08-09T02:50:00.123456+00:00",
  "telegram_user_id": 1020615388,
  "user_name": "Rajan",
  "state": "RenterState:waiting_for_requirement",
  "event_type": "LLM_CALL",
  "direction": "OUTBOUND",
  "status": "SUCCESS",
  "latency_ms": 412.5,
  "payload": {
    "provider": "groq",
    "model": "llama-3.3-70b-versatile",
    "schema": "RequirementExtractionResponse",
    "prompt": "Extract rental requirements from...",
    "response": {
      "is_complete": true,
      "preferred_locations": ["Manikonda"],
      "max_rent": 40000,
      "conversational_summary": "Got it! Looking for a 2BHK in Manikonda..."
    }
  },
  "error": null
}
```

## 4. Common Troubleshooting Scenarios

### A. "Why did the LLM give this unexpected answer?"
1. Run: `python -m app.tools.inspect_logs --user <id> --type LLM_CALL`
2. Check the `Prompt:` line to see what full conversation history was sent to the model.
3. Check the `Response JSON:` to see the exact structured output generated by Groq/Gemini.

### B. "Is the bot stuck or rate-limited?"
1. Run: `python -m app.tools.inspect_logs --errors`
2. If you see `RETRYING_429`, the model hit a rate limit and the provider is automatically backing off and retrying.
3. Check the `latency_ms` field to see how long the LLM took to reply.

### C. "Why didn't my message trigger the expected command?"
1. Run: `python -m app.tools.inspect_logs --user <id>`
2. Check the `state:` field in the event header to see what FSM state the user was in when the message was received.
